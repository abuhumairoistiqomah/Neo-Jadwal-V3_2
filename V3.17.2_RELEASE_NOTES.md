# E-JADWAL V3.17.2 RC1 — leave maintenance, privileged submission, and red absence status

Baseline: V3.17.1 RC1. Staging candidate; not verified against live Supabase.

**Schema hotfix:** migration version renamed from `202610180001` to unique `202610180002` to avoid collision with V3.16.2. See `HOTFIX_V3_17_2_SCHEMA_INSTALL.md` and the read-only schema check.

## Installation

1. **Back up the database and source.** Apply `supabase/migrations/202610180002_v3_17_2_leave_maintenance_staff_submission.sql` in **staging first**. This migration is mandatory for the new admin menu and authenticated staff shortcut. Apply SQL **before** deploying the frontend.
2. Extract this patch over the **V3.17.1 project root** (the directory with `package.json`) OR use the full source. **Do not overwrite a customized `.env.local`**.
3. Run `npm.cmd test`, `npm.cmd run lint`, `npm.cmd run build`, `npm.cmd run dev` on Windows.
4. Smoke test: (a) Wednesday Ajeng official duty cells are red and say NOT teaching, (b) admin menu List Badal Pengajuan Badal appears under Persetujuan Izin, (c) future approved request appears, past hidden unless toggled, (d) edit JP across joined classes updates leave request periods, request slots, coverage and task JP atomically, (e) soft delete hides approved leave/coverage from schedules and statistics; restoration revalidates, (f) guest still needs screenshot, authenticated staff may submit without screenshot, and direct approval requires a written oral-authorization note.

## Design constraints and intentional limitations

- `TUGAS_RESMI` in **Jadwal Pribadi** is colored red (absence; not teaching). `BADAL` retains separate teaching status/color. No schedule master records are changed.
- Approved leave list displays up to the **250 latest approved/deleted-approved requests** per load. Past and soft-deleted entries have independent checkboxes. A future pagination release may expand older history.
- **Edit JP moves the whole existing teaching session (all involved canonical classes)** from JP1–JP6 to another JP on the same date, provided the absent teacher actually teaches in all of those classes in the target period, no target conflicts, and substitute rules remain valid. It updates coverage period, request slots (including subject & schedule reference), attendance JP, and teacher-owned task JP **within one server transaction**. It **does not change classes**, insert previously omitted class sessions, change FREE JP, or handle JP0. Requests whose tasks span multiple leave dates are rejected rather than rewritten ambiguously. For changed classes or absent slots, use a future dedicated class/coverage repair workflow.
- Soft delete is **whole-request**: status moves from APPROVED to CANCELLED with `deleted_at` and previous-status audit, and related coverage + task rows get `deleted_at`. Original data remains for auditing. Restore validates schedule and conflicts; it can fail legitimately if newer data blocks restoration.
- Authenticated staff bypass **only** applies to verified `ADMIN`/`WAKASEK` accounts, checked again by Postgres `auth.uid()` and `current_user_is_staff()`. Frontend Admin Mode alone cannot bypass proof. Default submission without proof still enters SUBMITTED queue; optional direct approval requires explicit authorization note and is atomic. Non-staff/guest v4 screenshot flow is unchanged. Immediate approval does not support uploading new Drive task files during the same click: use task links or submit to queue before uploading.
- There is no migration affecting education calendar, master timetables or translations; new menu labels are translated to English/Arabic, key actions receive baseline translations.
